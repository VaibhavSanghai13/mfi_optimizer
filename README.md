# MFI Route Optimizer

Plans daily routes for microfinance (MFI) field officers who ride two-wheelers to village **JLG (Joint Liability Group) meetings**. Each meeting has a weekday, a time window, a duration and a priority; officers have shifts and a lunch break. The app decides **which officer visits which meetings, in what order and when**, so urgent meetings are covered and road travel is short — a Vehicle Routing Problem with Time Windows (VRPTW) solved with **Google OR-Tools**.

* **Manager:** manages branches, officers, JLG groups and users; generates synthetic data; plans routes on a map with a timeline; saves plans; changes settings.
* **Field Officer:** signs in on a phone and sees **My Day** — their own route with Google Maps navigation per stop.

Data is **synthetic JLG groups on real Baramati-taluka villages** (real JLG data is private), plus manual entry forms with a map picker.

## Architecture in one minute

| Part | What it does |
|---|---|
| **Next.js** (App Router, TypeScript, Tailwind, shadcn/ui, React-Leaflet) | all pages and the TypeScript API routes (`app/api/*`) |
| **Prisma → Supabase PostgreSQL** | the only database access; RLS on every table |
| **Own JWT auth** (bcrypt, `jose`, httpOnly cookie, `proxy.ts`) | two roles: Manager and Field Officer |
| **Travel times** (`lib/travel/`) | public OSRM server (car times × two-wheeler speed factor), cached in PostgreSQL |
| **Python function** `api/optimize.py` (FastAPI + OR-Tools) | the solver; a pure function — it never touches the database |

`lib/plans.ts` glues them together: database → travel matrix → optimizer → road geometry → saved plan. One Vercel deployment serves everything.

## Prerequisites

- Node.js 20+ and npm
- Python 3.11+

## Local setup

```bash
# 1. Node dependencies (also generates the Prisma client)
npm install

# 2. Python virtual environment + dependencies
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt

# 3. Environment variables
copy .env.example .env          # macOS/Linux: cp .env.example .env
```

Then fill in `.env` (never commit it).

## Run

With the virtual environment activated:

```bash
npm run dev
```

This starts both servers with `concurrently`:

| Server | URL | Notes |
|---|---|---|
| Next.js | http://localhost:3000 | the app |
| Python optimizer (uvicorn) | http://127.0.0.1:8000 | Next.js forwards `/api/optimize/*` here in development |

Check the optimizer: http://localhost:3000/api/optimize/health

## Village data

`data/villages_baramati.csv` (real Baramati-taluka villages) is built by three Python scripts from OpenStreetMap, the Census of India 2011 and DataMeet village boundaries. See [data/README.md](data/README.md).

```bash
pip install -r requirements-data.txt
python scripts/data/fetch_villages.py
python scripts/data/fetch_census.py
python scripts/data/join_census.py
```

## Travel times

Road travel times come from the public [OSRM](https://project-osrm.org/) server and are cached in the `travel_cache` table (`lib/travel/`). The notebook `scripts/notebooks/travel_time_comparison.ipynb` compares straight-line and road distances on a map:

```bash
python -m jupyter notebook scripts/notebooks/travel_time_comparison.ipynb
```

(Use `python -m jupyter` with the venv activated, so the venv's Jupyter and packages are used.)

## Database

The data model lives in `prisma/schema.prisma`. Each change becomes a SQL file in `prisma/migrations/<timestamp>_<name>/migration.sql`: generated by Prisma, plus hand-written check constraints and Row Level Security at the end.

**Set up a database** (Supabase free project), either way:

- **SQL editor:** run every `prisma/migrations/*/migration.sql` in order in the Supabase SQL editor.
- **Prisma CLI:** with `DATABASE_URL` and `DIRECT_URL` in `.env`, run `npx prisma migrate deploy`.

**Load the demo data:**
1. Set `SEED_PASSWORD` in `.env` (12+ characters) — the initial password of every seeded account. It is never committed.
2. Generate the seed and run it in the SQL editor (after the migrations; safe to run more than once):

```bash
npm run seed:sql
```

The same inputs (including `SEED_PASSWORD`) always give an identical file (fixed seed, fixed ids, deterministic salts).

## Deployment

The app is deployment-ready for **Vercel + Supabase** (free tiers). Follow [docs/deployment.md](docs/deployment.md).

**Changing the schema** (never `prisma migrate dev` or `db push`):

1. Edit `prisma/schema.prisma`.
2. Generate the SQL without changing the database (it only *reads* the live schema; first set `$env:DIRECT_URL` in the shell to the value from `.env`):
   `npx prisma migrate diff --from-url "$env:DIRECT_URL" --to-schema-datamodel prisma/schema.prisma --script`
3. Save it as a new `prisma/migrations/<timestamp>_<name>/migration.sql`, append any hand-written SQL, and run it in the SQL editor.
4. Never edit a migration that has already been applied.
